Vibe Coding Workflow · The New Operating Model

Your spec is no longer the input. It's the output.

The shift from traditional PM workflow to Vibe Coding isn't just about speed — it's about what you trade. Static documents that represent guesses for live links + extracted specs that represent proven logic.

Old Way · Dependency Loop
Build to Spec
Research→ Write Spec→ Wait for Eng / Design→ Review Build→ Feedback→ Wait for Update
The Spec is your starting point — a best guess at requirements before any code is written. You're a requestor, dependent on other people's time to validate a hypothesis you can't prove yourself.
⚠ The spec is the input · You trade guesses for guesses.
New Way · Vibe Loop
Build to Spec
Idea→ Build Prototype→ Test & Iterate→ Extract Spec→ Connect Infra→ Live
Your prototype is the source of truth. You manifest the logic, test the live app, iterate in real time. The Spec is the output — evidence of validated logic, not a wish list.
✅ The spec is the output · You trade live links for live links.

The Production Threshold

Not every prototype should move into production.

Threshold judgement is the most important PM skill in Vibe Coding. Move too early and you harden a build that still needs to change. Move too late and the AI's complexity outpaces your ability to manage it.

✅Move to Production Spec when
  • Your "kill switch" hypothesis is proven with functional evidence.
  • Stakeholders have approved the direction for a real build.
  • You can explain the logic without needing a demo.
  • Your goal has shifted from discovery to durability.
🚫Stay in Prototyping mode when
  • Your core value proposition or user flow is still changing.
  • You haven't gathered feedback outside your immediate team.
  • You can't yet define the business rules the AI is executing.
  • Speed of iteration is still more valuable than system stability.
If you don't transition at the right time, you hit a ceiling where the AI's complexity outpaces your ability to manage it. Or you waste hours hardening a build that's still going to change.
Paying Off Your Comprehension Debt

The Living PRD is your translation layer.

Comprehension debt — where the AI knows the logic better than you do — comes as a trade-off to vibe coding speed. The Living PRD forces the AI to explain the logic it manifested during the build, creating a repeatable source of truth.

The Eight Building Blocks of a Living PRD

What you're extracting — eight blocks, one professional-grade spec.

By extracting these eight blocks, you turn a black box of AI code into a documented system for handoff.

🔎
Product Overview
High-level summary of the validated system — what it does and who it's for.
🎯
Problem & Hypothesis
Clear definition of user friction and the evidence-backed intervention being tested.
🗺️
User Flow & Screen Map
Visual and descriptive map of navigation paths, screen states, and interactive logic.
📈
Success Metrics
North Star metric and leading indicators used to measure production performance.
🛠️
Technical Reality
Truth vs. Mock report — functional logic vs. mocked elements and current infra connections.
⚠️
Assumptions & Risks
Current confidence levels, kill switch triggers, and potential technical failure points.
🧱
In vs. Out Scope
Definitive list of included features, excluded items, and proposed roadmap for future phases.
📋
Engineering Recommendation
Strategic guide on build order, technical effort estimates, and open architectural questions.
Example Snapshot

What a Living PRD actually looks like.

Snapshot of the eight blocks from the SnapWishlist Living PRD — a multimodal AI feature that turns travel inspiration photos into bookable Airbnb wishlists. Showing the first four blocks here; the full sample lives in your repo.

🔎 SnapWishlist · Living PRD 04-structure/PRD.md (excerpt)
🔎 Product Overview
Multimodal-AI feature that analyses user-uploaded travel inspiration photos, identifies locations and vibes, then surfaces matching Airbnb listings in a personalised wishlist carousel. Target: "The Visual Planner" — Gen-Z/Millennial traveler who plans by aesthetic, not price.
🎯 Problem & Hypothesis
Friction: users find inspiration on social media but can't bridge from saved photo to bookable listing. Intervention: if we allow photo upload + AI listing match, wishlist creation will increase and discovery drop-off will decrease — prototype testing showed >80% location accuracy.
🗺️ User Flow
5 screens: Homepage → Photo Upload → AI Analysis Loading → "Found it!" Results → Save to Wishlist. Edge cases handled: non-travel photo error, face-blur for privacy, generic vibe fallback to tag-based search.
🛠️ Technical Reality
Functional: image upload, multimodal AI call (GPT-4o), location tag extraction, wishlist save flow. Mocked: listing DB is a JSON file (not live Airbnb data); Visual Similarity Score hardcoded — not a real ML model.
The honest part Notice the "Mocked" column. The whole point of the Living PRD is to document reality — including what doesn't work yet. That's how an engineer trusts you.

The Three Pillars of an Engineering-Ready System

You don't need to be an engineer.
You need the AI to set up the infrastructure.

These three pillars are the non-negotiable standards for moving any prototype into a production environment. Skip these and you aren't handing over a product — you're handing over a mess.

01 · The Front Door
📂
GitHub Connection
The project must live in a version-controlled repository with permanent history, safe rollbacks, and a secure front door for technical collaboration. This is where the engineer goes to clone your code on day one.
02 · The Cleanup
🧱
Code Refactoring
The codebase must be structurally organised with professional naming, separated logic, and a README so an engineer can fully orient within 5 minutes. No more Component_1 spaghetti.
03 · The Memory
🗄️
Supabase Connection
The system must move from mocked data to a persistent PostgreSQL database with an Auth layer, managed through a visual table editor rather than hard-coded simulations. Your product now has memory.
You direct, the AI executes and connects. By checking these three boxes, you're effectively paying off your technical debt — moving from a temporary builder link into a structured, version-controlled system.

Key Takeaways

Transition from prototypes to production specs.

01
Shift the operating model. Product Managers move from the dependency loop of hypothetical specs to a vibe loop of functional evidence. The PRD becomes a validated output, not a document of unproven guesses.
02
The Living PRD automates documentation. Extract the hypothesis, data context, and prompt chains used during construction. The technical handoff becomes an effortless byproduct of the build process — not a new project.
03
Enforce technical rigor. PMs must refactor AI code into structurally organised, production-ready assets. Connect functional builds to version-controlled repos and live databases — that establishes the durability required for live environments.
Optional · Dig Deeper

Push past the minimum.

Optional exercises to stress-test the infrastructure you just stood up.

01
The Repo Rollback Drill
Once connected to GitHub, intentionally break a core feature with a reckless prompt. Use your commit history to revert to the last stable version. Does your version control act as a functional safety net, or do you lose your technical reality the moment a prompt goes wrong?
02
The Data Integrity Stress Test
Open your Supabase dashboard and manually add bad data — negative price, missing required field. Refresh your prototype to see how the UI reacts. Does your behavior logic catch the error gracefully, or does the system crash when the database stops playing by the rules?
