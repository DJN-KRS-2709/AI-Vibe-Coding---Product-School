The Integration Chain — 3 Prompts

Prompt 1 — Database Schema
"Create a 'users' table and an 'invites' table in Supabase. When a user sends an invite on Screen 2, store it with sender email, recipient email, and timestamp. When the team workspace loads, fetch all invites for this user. When the PM dashboard loads, calculate actual invite rate from real data."
Prompt 2 — Authentication
"Add Supabase authentication. Login/signup screen. After login, fetch only their team's invites. Different users see different data. Show logged-in user's name in header. Add logout."
Prompt 3 — Edge Cases
"Handle failure modes: connection fails → error message. No invites → empty state + CTA. Invite fails → error + retry. Add loading skeletons while fetching."

How Lovable Connects to the Real World

Three integration patterns you'll use today:
🗄️
1. Database (Supabase)
Your data lives in tables. Read, write, update, delete. The AI writes the SQL and API calls. You describe what data to store and when to fetch it.
🔐
2. Authentication (Supabase Auth)
Signup, login, logout, sessions. You describe who should see what. Row-level security means users only see their own data.
🔌
3. External APIs (Stripe, SendGrid, any API)
The AI reads the docs and writes the integration. You describe the trigger and the action.

You don't write the code. You describe what should happen. The AI integrates it.

Real Products Break. Yours Should Break Gracefully.

The 5 edge cases every product needs:
1
Loading
What does the user see while data is being fetched? Skeleton screens, spinners.
2
Empty
What if there's no data yet? Helpful message + CTA, not a blank screen.
3
Error
What if the API fails? Error message + retry, not a crash.
4
Conflict
Two users do the same thing simultaneously? Last-write wins, or merge.
5
Boundary
10,000 items instead of 10? Pagination, not a frozen page.

If you can describe the failure, the AI can handle it.

Security Checklist — The One-Page Version

You're a PM, not a security engineer. But know the basics.
✓ Do
  • Use Supabase Row-Level Security (RLS)
  • Use HTTPS (Lovable defaults this)
  • Never expose API keys in frontend code
  • Hash passwords (Supabase Auth auto-handles)
✗ Don't
  • Store sensitive data you don't need
  • Skip auth "because it's just a prototype"
  • Trust user input — validate server-side

This is a prototype, not production. But good habits start now.

Cautionary Tale · 10 Minutes

The Product That Never Handles Errors

A real product with a database, auth, and API integrations — but zero error handling.
Slow network →
Infinite loading, no feedback
Invalid email →
Silent failure, user thinks it worked
Database unreachable →
Blank screen, no explanation
Two users, same record →
Last write wins, data lost

A backend without error handling is worse than no backend at all.

Users trust that "real" products work. When yours doesn't tell them what went wrong, they blame the product.
