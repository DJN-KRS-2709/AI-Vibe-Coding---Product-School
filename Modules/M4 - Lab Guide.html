1

Extract Your Living PRD

Individual Exercise · 15 minutes

Prompt Lovable to interrogate your current build and generate a structured PRD. Your goal is to capture a truth report of your prototype's functional logic, screen map, and technical reality.

🛑
Do NOT attempt to "fix" the code yet. The goal is to document what really exists, even if it's not perfect. Document reality first — refactor in Phase 2.
1
Prompt Lovable to extract your PRD
5 minutes
Open Lovable and return to your current prototype. Paste this prompt into the chat:
Living PRD Extraction Prompt
"Extract a PRD from this prototype covering: what it does, who it's for, the problem it solves, all screens and their purpose, the user flow, the hypothesis, key metrics, and what is mocked versus real."
Hit enter and wait for the full output before doing anything else.

If Lovable seems confused about what the product is, follow up with: "Audit the existing files and our previous conversation to find these details."
2
Review the output
5 minutes
Read through the PRD in the Lovable chat. Audit it against three questions:
Does it accurately list all the screens you built?
Does it correctly identify what's real vs. mocked?
Is the hypothesis and technical reality honest about the current state of your build?
💡
Remember: it's completely fine if your PRD shows your database isn't connected or your logic is still mocked. You're not losing points for missing features — you're gaining points for documenting the truth.
3
Push your PRD to GitHub
5 minutes
Once you're happy with the output, prompt Lovable:
Save & Push Prompt
"Save this as 04-structure/PRD.md and push it to my connected GitHub repository."
Open your GitHub repository and confirm PRD.md appears in your file tree before moving on. If the file doesn't appear, re-prompt: "Push all current project files to my connected GitHub repository."
📙
Phase 1 deliverable: 04-structure/PRD.md committed to your GitHub repo. If it's not in GitHub, it didn't happen — Phase 2 depends on this file.

Refactor Your File Structure

Lab Step 1 · 7 minutes

Rename your generic Component_1 files into descriptive, human-readable names. Use the screen names you just documented in PRD.md.

1
Open PRD.md in your GitHub repo
Open your 04-structure/PRD.md file in GitHub (the one you just pushed in Phase 1). Scroll to the User Flows & Screen Map section — copy your list of screen names. You'll paste these into the refactor prompt next.
2
Paste the refactor prompt into Lovable
Replace [list your screen names] with the actual screens from your PRD:
Refactor Prompt
"Refactor this codebase. Rename components: [list your screen names from your PRD]. Separate data logic from display components. Group files by feature. Add a README.md explaining the flow and project structure."
💡
Tip: the more specific your screen names, the better the refactor. TeamValueScreen and InviteFlow are better than Screen 1 and Screen 2.
3
Verify the refactor
Switch to the Code tab in Lovable. Open src/pages. Confirm:
File names are descriptive (no more Component_1.tsx)
A README.md appears in your file tree
Click into the README — it lists your screens and explains the flow
If you still see generic names, re-prompt: "Rename the files in the src/pages directory to match the names in my PRD."

Generate the Engineering Handoff

Lab Step 2 · 7 minutes

Force the AI to summarise the work it just did into a technical manual an engineer can inherit cold.

1
Paste the handoff prompt into Lovable
Engineering Handoff Prompt
"Generate an engineering handoff for this prototype. List every component and its purpose. Describe the data model. Note what is mocked versus real. Write a Start Here guide explaining how the project is structured and where an engineer should begin."
2
Review the output
Read through the generated handoff. It should clearly explain:
Which files handle the data and which handle the UI
What's mocked vs. real (matches your PRD)
A clear Start Here guide for a new engineer
Make any tweaks if necessary. If the handoff misses a major component, prompt: "Update the handoff to include [X component]."
3
Save HANDOFF.md to GitHub
Prompt Lovable:
Save Prompt
"Save this as HANDOFF.md and push it to my connected GitHub repository."
Open GitHub and confirm HANDOFF.md appears in your file tree. This is the artifact you'll swap with your peer in Phase 6 — it must be on GitHub before that.

Show and Swap Your Spec Handoff

Breakout Pairs · 10 minutes

Pair up. Read your partner's PRD.md and HANDOFF.md in total silence for 3 minutes — no verbal context. If they get confused, that's the data. Then ask the three questions.

A
Choose how to share your repo
Before you begin, choose one option to share your files with your partner:
  1. Screenshare — the simplest option. Navigate to PRD.md and HANDOFF.md in GitHub so your partner can read along in real time.
  2. Add as a collaborator — Settings → Collaborators → add their GitHub username. Recommended — mirrors how real engineering teams share code.
  3. Make repo public — Settings → Danger Zone → "Change visibility." Anyone with your link can view it.
B
Silent reading: 3 minutes per side
Spend 3 minutes reading your partner's PRD.md and HANDOFF.md in total silence. Do not explain your logic. Do not justify if you see them pausing. If they're confused by a step, let them stay confused — that is your data.
C
Ask the three questions — take notes
After silent reading, the reader answers; the writer takes notes. Then swap.
1
Product Value: Can you identify the What / Who / Hypothesis in under 60 seconds? (Based strictly on the Product Overview, do you know exactly what the app does and the specific problem it's testing?)
2
Technical Reality: Is Real vs. Mocked clear enough that you aren't guessing what works? (If you clicked a button, would the documentation accurately predict if it actually saves data or just shows a fake success message?)
3
Engineering Handoff: Does it tell you exactly which file or feature to open and build first? (Is there a clear, plain-English "Start Here" instruction pointing to a specific screen or file?)
📝
Capture the feedback in GitHub. Create 04-structure/swap-notes.md and paste your partner's three answers + any pain points. This becomes input for tightening your PRD before M5.
