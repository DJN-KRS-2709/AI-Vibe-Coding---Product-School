Extract Your Living PRD

Individual Exercise · 10 minutes

Use the Living PRD Extractor tool to interrogate your current build and generate a professional specification. Your goal is to capture a truth report of your prototype's functional logic, screen map, and technical reality.

🛑
Do NOT attempt to "fix" the code yet. This is pre-work to document the current state of your prototype, even if it's not perfect. Document the reality first.
🔗 Open Living PRD Extractor Tool
1
Configure the Extractor
3 minutes
Open the Living PRD Extractor and select "Build Your Own". The recommended path: paste your 03-prompt-chaining/prompts.md directly from your GitHub repo into the "Paste from GitHub" textarea, or drop the file from your local clone. (Your GitHub repo is the canonical record — the tool can also try to auto-import from M2/M3 browser cache, but treat that as a fallback.) The tool generates a baseline Extraction Prompt with variables you must customize:

Replace the brackets with your actual product details — your screens, your hypothesis, your metrics. The AI needs to know which evidence to audit.
💡
Pro Tip: Don't overthink the hypothesis or metrics. Use the ones you've been building toward since Module 1. They're already embedded in your prototype.
2
Run the Technical Interrogation
5 minutes
Copy your customized prompt from the Extractor tool and paste it into your existing Lovable chat for your M3 project. Hit enter and wait for the AI to output the structured report.

If the AI starts asking you what the product is instead of auditing the code, respond with:
Fallback Prompt
"Audit the existing files and our previous conversation to find these details."
3
Paste the Output Back Into the Extractor
2 minutes
Once the AI finishes generating the specification, copy the entire response and paste it back into the Living PRD Extractor. This populates your engineering-ready blocks.

Read through each block and verify:
Functional Architecture — does it accurately list the screens you built?
Technical Reality — does it correctly identify what is real (connected code) versus mocked (static UI)?
Hypothesis and Metrics — do they match what you've been testing since M2?
✅
It is completely okay (and expected!) if your PRD shows that your database isn't connected or your logic is still mocked. You aren't losing points for missing features — you are gaining points for documenting the truth.
Living PRD — Notes
Flag anything the AI misrepresented, missed, or any mocked features you need to revisit during the next lab.

Where to find your list: Look at the User Flows & Screen Map section of the Living PRD you just generated. Replace [list] with the actual names of your screens.

Connect Your Infrastructure

Lab Exercise · 10 minutes

Move your project from a temporary session to permanent version control and a real database. This infrastructure is a mandatory prerequisite for Module 5, where you'll build real authentication and data relationships.

Two clicks. Your code gets a real GitHub repository and a real database.
This is the moment your prototype stops being a demo.

Part A — Version Control with GitHub

1
Open the GitHub Connection
From the navigation bar of your Lovable project, click the GitHub icon in the top-right corner.
2
Connect to GitHub
Click "Connect to GitHub" and follow the authorization steps. You'll be prompted to authorize lovable.dev access to your GitHub account. Grant the access.
3
Confirm the Transfer
You may see a confirmation message about transferring your project to set up 2-way sync. This is expected — it means your code is being upgraded from a temporary Lovable file to a permanent GitHub repository.
💥
Don't Panic: If you see a warning about "moving the only instance" — that's exactly what we want. You're upgrading your project to real version control. Confirm the transfer.
4
Verify in GitHub
Open your GitHub repo URL in a new browser tab. Browse the code. Find your refactored component names. See the README. This is what an engineer sees when they clone your project.
GitHub connected — your code is in a real repository
Repo verified — you can see your refactored files and README in GitHub

Part B — Connect Your Database Backend

Transition your data from mocked variables to a real, live database. This allows your app to save information across sessions.

1
Trigger the Backend Connection
In Lovable, prompt the AI with a feature that requires a database. For example: "Save user onboarding progress to the database so returning users resume where they left off." Lovable will prompt you to enable the backend — click Allow.
2
Verify the Backend
Open the backend dashboard (check Settings in Lovable). You should see a live database, authentication, and storage provisioned for your project. This is the infrastructure you'll build on in Module 5.
💡
Depending on your Lovable setup, the backend may be Lovable Cloud (built-in) or a Supabase connection. Either way, you'll end up with a real PostgreSQL database. If your instructor directs you to connect a separate Supabase account, follow those instructions instead.
Backend connected — your prototype has a real database
Dashboard verified — you can see the database in the settings/dashboard

Your prototype just made the transition.
It has a spec, clean code in GitHub, and a real database.
This isn't a demo anymore.

The Inheritance Test

Breakout Groups of 2 · 15 minutes

This is the most honest handoff test in the course. Instead of reading your partner's documentation yourself, you're going to clone their repo into your AI tool and let the agent explain the product. That's how PMs at Indeed, Linear, Vercel, and other AI-fluent teams actually collaborate today: the repo is the spec, the agent is the reading interface. No Confluence. No 30-page doc nobody opens.

Swap ONLY your GitHub repo URL.
No verbal walkthrough. No screen share of Lovable. Just the link.

1
Swap repo URLs in the chat
1 minute
Post your GitHub URL. Grab your partner's. Do not explain anything. If your partner asks "what does this do?" — point them at the repo.
2
Clone your partner's repo into your AI tool of choice
2 minutes
Use whichever AI tool you already have — Cursor, Claude Code, Lovable's import-from-GitHub, or ChatGPT with the repo files attached. The tool doesn't matter. What matters is that an agent reads the repo, not you.
💡
Don't have Cursor or Claude installed? Open ChatGPT, attach the README + PRD + handoff markdown files from the repo, and treat that as your agent. Same exercise, lower friction.
3
Ask the agent these 5 questions
5 minutes
Paste all 5 at once. Let the agent answer from the repo alone. Copy the agent's answers below.
1
What does this product do, and who is it for?
2
What hypothesis is it testing?
3
What's real vs. what's mocked?
4
What are the 3 biggest technical decisions an engineer needs to make next?
5
If you had to ship a fix on Friday, which file would you open first?
4
Compare the agent's answers to your partner's actual intent
5 minutes
Walk through the agent's answers together. Where did it get it right? Where did it guess, hallucinate, or miss the point? Every gap is a gap in your partner's repo — not the agent's failure. Swap roles and run it again.
🔍
Watch for the silent gaps. Agents don't politely paper over confusion the way a human reader does. If the agent says "this appears to be a dashboard for X" when your partner meant Y — that's the kind of ambiguity an engineer would silently misinterpret and ship the wrong thing. Fix those gaps before Module 5.
Inheritance Test — Agent Answers vs. Reality
For each question: what did the agent say, and what did your partner actually mean? Where the two diverge = revision priorities for your repo.
Slack debrief — post one sentence
The biggest gap my partner's agent surfaced about my repo was ___.
