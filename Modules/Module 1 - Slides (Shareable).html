Lecture

You never start from a blank canvas.

Modern vibe-coding tools are multimodal. Three entry points, three jobs.

📝
Text-to-App
0 → 1. Natural-language prompt, no design exists yet. Cures blank-page syndrome for greenfield ideas.
📸
Screenshot-to-App
1 → N. Upload a pattern (Mobbin, your own product). The AI clones the layout, palette, navigation.
🎨
Design-to-Code
On-brand from minute one. Paste Figma frames or design-system tokens. Eliminates "looks like a toy" stakeholder pushback.
When to use which
  • Text-to-App — exploring a new bet, no precedent. Lab 1 today.
  • Screenshot-to-App — refining a vibe sketch against a professional pattern. Lab 2 Path A today.
  • Design-to-Code — prototyping inside an existing product (your real day job). Lab 2 Path D today.

Lecture

Vibe Coding Credit Efficiency

Credit efficiency extends your runway. Strategic resource management ensures your credits are spent on high-value architectural shifts — not low-value trial and error.

01
Plan in a Sandbox
Structure your prompts and iterate on logic in an external LLM first. Do ~60% of the refinement work in ChatGPT, Gemini, or Claude — free — to lock the instruction before burning a single credit.
02
Paste into Tool
Only move to Lovable when the prompt is polished. Treat the tool as your execution engine, not your scratchpad. Aim for one generation, not trial-and-error on half-baked instructions.
03
Adjust Code Directly
Fix minor typos, colors, or alignments directly in the code panel. Save your build credits for major structural changes or new feature injections — not cosmetic tweaks.
⚠
When to Eject
If a prompt fails twice, stop. Export the code to an external tool to debug, then paste the fix back. Never enter a "credit death spiral" by re-prompting the same broken logic.

Reflection · 8 min

Walk your build as if you've never seen it.

Three minutes silent · two minutes notes · three minutes AI critique.

StepWhat to do
3 min silent walkOpen your link in a fresh tab. Don't explain anything. Click as a first-time user. Notice where you hesitate.
2 min notesAnswer in writing: what's immediately clear · what's confusing · what assumption am I testing?
3 min AI critiquePaste the link + the AI-review prompt (below) into ChatGPT or Claude. Read the critique. Pick one fix.
AI-Review Prompt (copy-paste verbatim)

You are a senior product reviewer. I built a prototype to explore the following assumption: [paste your one-sentence assumption]. The link is: [paste]. Critique the build on three dimensions: (1) Does the first screen communicate the core value in under 10 seconds? (2) What's the single biggest source of confusion? (3) What's the one change that would most increase my confidence in this direction? End with the question you would ask the user if you could only ask one.

Distinction

From toy to tool.

The most important distinction in vibe coding. Internalize it and the rest gets easier.

The Toy
Looks impressive. Proves nothing.
  • Generates applause, not insights.
  • No logic behind the screen.
  • Dies after the demo.
  • Can't survive a real user.
The Tool
Looks real. Proves something works.
  • Validates an assumption with clickable evidence.
  • Handles at least one real user flow end-to-end.
  • Survives when someone else uses it.
  • Generates a decision, not a reaction.

The score you gave yourself — was it a toy or a tool? That gap is what the rest of this course closes.

Key Takeaways

Execute Vibe Coding Velocity

Build to think, not to ship. Today's two prototypes were not products. They were thought experiments rendered in pixels. Slack's entire pivot started this way — a tool the team built to talk to each other while making a game.

Vibes become tools through intentional, incremental layers. Design match, interactivity, surgical refinement — three compounding passes, no rebuilds. Starting over is the most expensive mistake in vibe coding.

Every build must move the Confidence Line. A prototype is a tool only when it answers a real question. Slack's "2,000 messages" magic number was generated by a working product — not a meeting.

Credits are fuel. Plan in a sandbox. 60% of your prompt work happens outside the tool. The tool is for committing the plan, not finding it.

The mental barrier is gone. You shipped functional software twice today without writing a line of code. The wall between thinking and building is removed. Every M2–M6 deliverable assumes you can already do this.
