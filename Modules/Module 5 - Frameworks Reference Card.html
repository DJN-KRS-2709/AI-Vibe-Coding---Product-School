1. The Three Integration Pillars

Move from a connected infrastructure to a product fully built on the database. Every prompt for an integration falls into one of three pillars — schema, ownership, external orchestration.

PillarVerbExample prompt
🗄️ Schema Expansion
Define your source of truth.		 Extend tables, types, and relationships. Replace hardcoded UI with real queries. "Extend the schema. Create an 'Invites' table with sender_email, recipient_email, status, timestamp. Replace hardcoded dashboard metrics with real queries from this table."
🔐 Ownership Permissions
Partition the data.		 Row-Level Security — users can only see records tied to their authenticated session. "Ensure users can only see records where the 'user_id' matches their authenticated session ID."
🌐 External APIs
Orchestrate beyond your DB.		 Document the trigger + action. Plug in Stripe, SendGrid, OpenAI, etc. "Connect the Stripe API. Trigger a checkout session when 'Upgrade' is clicked and return to the dashboard on success."

Rule: you are no longer prompting for pixels. You are prompting for technical transactions.

2. The Four Product States — Resistance Engineering

Most prototypes fail because nobody described what should happen when things go wrong. If you can describe the failure mode, the AI can build the safety net.

StateData GapAction to Take
📭 Empty "Day-zero" experience — new user with no records. Active empty state with a "Get Started" CTA. Never a dead-end blank screen.
⏳ Loading Data takes time. Silence kills sessions. Skeleton screens that show the structure of the data before it arrives.
⚠️ Error APIs and DBs will fail or time out. Inline error with a Retry button. Graceful recovery, not a crashed session.
📊 Load-Bearing 5 rows → 5,000 in production. Pagination for large datasets. "Last-write-wins" for simultaneous edits.

Rule: every prototype passes the happy path. Every prototype fails at least one of these four states. Prompt 3 in your Integration Plan addresses all four in one shot.

3. The Stress-Test Trio — Chaos Before You Ship

Pick a chaos stressor. Run it. Document the result. Then ship — even if it failed (documented Known Gaps are still a ship).

TestWhat you doWhat "pass" looks like
⚡ The Kill Switch DevTools → Network → Offline. UI shows clear error message + Retry button — never a hung blank screen.
👻 The Ghost User Sign up with a brand-new email. Active empty state with a "Get Started" CTA — never an empty list.
🔥 The Spam Click Hit Submit 5× rapidly. One transaction in the database, not five duplicates.

Safari users: Safari has no built-in offline toggle. Use this Lovable prompt instead: "Simulate a database timeout on the [Main Screen] and show me the error state."

Rule: you never ship perfect code, you ship code with known risks. A documented Known Gap in HANDOFF.md is a professional ship. A silent broken feature is not.

6. The API Scaling Triangle — Future-Proofing

Your product is only as real as its ability to handle live, dynamic data. The three verbs that scale your product beyond your internal database:

VerbHTTP shapeReal-world analog
👤 Personalisation GET with the User-ID as a query parameter. Spotify "Discover Weekly" — your ID tells the API to fetch your mix, not the global top 40.
📡 Real-Time Utility WebSocket / polling for live feeds. Uber "Driver Tracking" — the app constantly calls a GPS API to update coordinates on your screen.
🔁 Continuity POST / PUT to sync state across devices. Netflix "Continue Watching" — your phone sends a timestamp so your TV can fetch where you left off.

Rule: the shift is from "my database is my product" to "my product is a switchboard." Any one of these verbs makes your demo meaningfully more alive.
