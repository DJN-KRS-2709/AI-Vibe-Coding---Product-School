Generate & Execute Your Integration Plan

Individual Exercise · 45 minutes

Paste the prompt below into Lovable with your prototype open. It will scan your project, generate a personalized Integration Plan with three customized prompts, and then you'll execute those prompts one at a time.

Part A — Generate Your Plan

1
Copy the Integration Plan Prompt
1 minute
Click the button below to copy the full prompt. Then paste it into your Lovable chat.
Integration Plan Prompt
Analyze this project and generate a markdown file called "Integration Plan.md" with the following sections. Base everything on what actually exists in this codebase — don't make up features or data that isn't here. ## Section 1: M4 Status Check Create a table listing: - How many screens this prototype has (count them) - Whether a Living PRD or product requirements document exists - Whether the code uses clean, descriptive variable and function names - Whether GitHub is connected - Whether Supabase or a database backend is connected For each item, fill in the actual status based on what you can see in the project. ## Section 2: Data Audit — What's Still Hardcoded? Scan every screen and component. Find every value that is hardcoded in the UI instead of coming from a real database query — metrics, counts, user names, dates, status labels, sample data. Create a table with three columns: - Screen / Component (where you found it) - Hardcoded Value (the exact value) - What It Should Query (the database table and calculation that should replace it) ## Section 3: Schema Design List every database table that currently exists. Then, based on the Data Audit, propose any new tables or fields needed to replace hardcoded values. For each table, list every field with its type (uuid, text, int, boolean, timestamp, jsonb) and a short note on its purpose. Mark which tables are new vs. existing from M4. ## Section 4: Auth Model & Permissions Based on this product's screens and user flows, define: - What user roles exist or should exist (e.g., regular user vs. admin, buyer vs. seller) - What each role can see and do - Row-Level Security rules — which tables need per-user data isolation, and what the policy should be ## Section 5: Prompts Generate three ready-to-use prompts that I can paste back into this tool one at a time. Each prompt should be specific to THIS project — use real table names, real screen names, real field names from this codebase. ### Prompt 1 — Schema Expansion A prompt to extend the database schema, create any new tables from Section 3, and replace all hardcoded UI values identified in Section 2 with real database queries. ### Prompt 2 — Auth UI + Row-Level Security A prompt to add a login/signup screen, implement the roles and RLS policies from Section 4, show the logged-in user's name in the header, add a logout button, and ensure different users see different data. ### Prompt 3 — Edge Cases A prompt to handle these failure modes across the entire app: - Database connection failure → error message with retry button (not a blank screen) - Empty data states → helpful message with a call-to-action (not an empty list) - Form submission failure → inline error that preserves user input - Loading states → skeleton screens on every screen that fetches data - Session expiry → redirect to login with a message Each prompt should be inside a code block so I can copy it easily. ## Section 6: Edge Case Checklist Generate a checklist of every edge case this specific product should handle. Include the five from Prompt 3 plus any product-specific ones. Each checkbox should have a bold label and a one-line description. ## Section 7: Stress Test Plan Create three named stress tests tailored to this product: - One that tests connection failure (e.g., going offline mid-action) - One that tests empty/new user experience (signing up fresh, zero data) - One that tests rapid repeated actions (spam-clicking submit, double-booking, etc.) For each test, describe exactly what to do and what the expected behavior should be. ## Section 8: Handoff Note Create a handoff note template pre-filled based on what currently exists: - What's Real vs. What's Mocked (table with every major feature) - Database Schema Summary (one line per table) - Auth & RLS Model (who can see what) - Edge Cases Handled (leave blank — to be filled after the lab) - Known Gaps (leave blank — to be filled after stress testing) - Live URL (leave blank — to be filled after deployment) Format the entire output as clean markdown.
💡
Pro Tip: If the prompt is too long for Lovable's chat, break it into two messages. Send Sections 1–4 first, then Sections 5–8 with: "Continue generating the Integration Plan — now add these sections."

Audit your Data Status:

Hardcoded values found — did it catch all the placeholder metrics, counts, and user info in your UI?
Schema makes sense — are the proposed tables and fields correct for your product?

Define your User Status:

Roles are correct — does it know who your users are and what each role can do?
RLS rules make sense — is it clear which tables need per-user isolation?

Map your Error & Data Handling Status:

Edge cases covered — are the critical failure modes for your product included?

Part B — Execute Your Prompts

Your Integration Plan has three prompts customized to your project. Run them in order — each one builds on the last.

3
Run Prompt 1 — Schema Expansion
10 minutes
Copy Prompt 1 from your Integration Plan and paste it into Lovable. This extends your database and wires your UI to real queries — replacing every hardcoded value the plan identified.

Verify it worked:

Enter data and refresh — does the data survive a page refresh?
Dashboard metrics updated — are numbers now computed from real data, not hardcoded?
Change data, see numbers change — modify something in the app and watch the metrics update
🚨
Data didn't persist? Check Settings > Integrations in Lovable — is Supabase still connected? If the tables exist but data is gone, the issue is your fetch logic. Re-prompt: "The [table] exists in Supabase, but the UI is still showing hardcoded numbers. Update [Screen Name] to fetch from the [table]."
4
Run Prompt 2 — Auth + Row-Level Security
10 minutes
Copy Prompt 2 from your Integration Plan and paste it into Lovable. This adds a login/signup screen and partitions your data by user.

Verify with the two-account test:

Create Account A — sign up, log in, enter some data
Log out completely
Create Account B — sign up with a different email
Account B cannot see Account A's data — Row-Level Security verified!
🚨
Can't log in or access is blocked? In your Supabase Dashboard, go to Authentication > Providers and ensure Email/Password is enabled. If you can log in but see "Access Restricted" everywhere, re-prompt: "I am logged in as a [Role], but I cannot see the [Table] data. Update the RLS policy to allow [Role] to read from the [Table] where the ID matches."
5
Run Prompt 3 — Edge Cases
10 minutes
Copy Prompt 3 from your Integration Plan and paste it into Lovable. This adds loading skeletons, error messages, empty states, and retry logic across your app.

Verify at least two:

Loading test — refresh your most data-heavy screen. Do you see skeleton screens while data loads?
Error test — open DevTools > Network > Offline. Does a clear error message appear instead of a frozen screen?
💡
Skeleton screen too fast to see? Your connection might be too quick. Tell the AI: "Artificially delay the data fetch by 2 seconds so I can verify the loading skeleton is rendering correctly."
💡
Frozen UI with no error message? The error isn't being caught. Tell the AI: "The app is failing silently on a network error. Add a try/catch block to the fetch function and display a visible error message to the user."
6
Push to GitHub
2 minutes
Commit your Integration Plan markdown to GitHub. It lives alongside your Living PRD and engineering handoff from Module 4.

Two checkpoints before you move on:
Dashboard data is computed from real queries, not hardcoded.
Different accounts see different data.

Build Notes
Document what worked, what needed re-prompting, and any adjustments you made to the generated prompts.

Stress Test & Deploy

Lab Exercise · 15 minutes

Pick a chaos stressor. Run it. Document the result. Then ship it.

1
Choose Your Stress Test
5 minutes
Pick one. Don't spend more than 2 minutes deciding — the goal is to see how your system handles a single point of failure.
⚡ The Kill Switch
Open DevTools > Network > set to "Offline." Does your UI acknowledge the disconnection, or does it simply hang?
👻 The Ghost User
Sign up with a brand new email. Does the user see an active empty state with a CTA, or a blank screen?
🔥 The Spam Click
Hit your "submit" button 5 times rapidly. Does your database create 5 duplicate records, or is the transaction handled correctly?

Result:

Stress Test — What Happened?
Describe exactly what you observed. If it failed, what broke?
📝
If it failed: You have two options. Fix it now with one final prompt, or document it as a "Known Gap" in your Integration Plan handoff section and deploy anyway. Both are valid PM moves. Ignoring the flaw is the only mistake.
2
Update Your Handoff Note
3 minutes
Open Section 8 of your Integration Plan. Fill in Edge Cases Handled and Known Gaps based on your stress test results. This is the honest record of what your product does under pressure.
3
Deploy Your Product
5 minutes
Click Share (top-right in Lovable) → then Publish. Click "Continue" and then "Publish." Your product will be live in about 30 seconds.
