01 · The Problem

The gap between inspiration and a bookable trip.

Visual planners find travel inspiration on social media every day. Almost none of it becomes a booked stay.

Users save dozens of travel photos on Instagram — then sit in front of Airbnb's search bar with no idea what to type. The discovery flow is manual, slow, and disconnected.
The User
"The Visual Planner"
Gen-Z and Millennial travellers who plan trips by aesthetics and vibe, not by price or dates. Their workaround today is opening Instagram and Airbnb in two tabs and squinting back and forth.
The Pain
The translation cost
A saved photo is an emotion. Airbnb search is a keyword box. Bridging those two costs ~20 minutes per inspiration — most people give up before they get to a real booking.
02 · The Hypothesis

What I believed before I built.

The M2 hypothesis: photo → listings is the right shortcut, and the AI can be accurate enough to be useful.

Hypothesis Statement
If we let Visual Planners upload an inspiration photo and let AI surface matching Airbnb listings,
then wishlist creation will increase and drop-off in the discovery phase will decrease,
because prototype testing showed >80% location identification accuracy and clear intent-to-save signals from target users.
Why this one The riskier path would have been chasing a chat-style "travel planner" agent. Photo-in / listings-out is a much narrower bet — one screen, one model call, one observable outcome. Falsifiable in a single weekend of testing.

05 · The Validation

What the Validation Brief uncovered.

Four assumptions tested in M2. Two confirmed. One challenged. One pivoted scope.

Assumption 1 · Confirmed
AI can identify the vibe accurately
Test: 25 inspiration photos through GPT-4o Vision. Result: 84% location or vibe-tag accuracy. Takeaway: the model is more than good enough to ship a V1 against.
Assumption 2 · Confirmed
Users will save listings the AI surfaces
Test: 5 target users walked through a clickable prototype. Result: 4 of 5 saved at least one listing on first session. Takeaway: intent-to-save is real, not theoretical.
Assumption 3 · Challenged
Desktop is the right first surface
Test: asked the same 5 users how they'd actually use it. Result: 5 of 5 said mobile-first — "I'd never open a laptop for this." Takeaway: mobile responsive is a V1 requirement, not a V2 roadmap item.
Assumption 4 · Pivoted
Privacy controls don't need to be visible
Test: asked users about face-blur and photo-storage. Result: all 5 wanted explicit, surfaced messaging. Takeaway: added a visible "your photos are discarded after analysis" line at upload time.

07 · The Logic

The Core Prompt Chain.

Three prompts. One system. Constraint-grounding turns clever prompts into reliable behaviour.

01 Foundation Prompt
Build a 3-screen React + Tailwind app called SnapWishlist:
  1. Homepage with a single primary CTA "Create Wishlist from Photo"
  2. Photo upload screen accepting JPEG / PNG (max 5 MB)
  3. Results screen showing a horizontal carousel of 3-5 listing cards
Use a single-page route. Keep the visual language clean, white-space heavy,
Gen-Z aesthetic. Do not add user auth or pricing logic.
02 Feature Prompt · Multimodal AI call
On the upload screen submit, send the uploaded image to GPT-4o Vision with this system prompt:
  "Identify the location (specific landmark, region, or country) AND the visual vibe
   (cozy, minimalist, coastal, tropical, etc.) in this travel photo. Return JSON:
     { location: string, vibe: string, confidence: 0-1 }."
Then run a tag-based query against the mocked Airbnb JSON in /data/listings.json
and render the top 5 matches as listing cards on the results screen.
03 Guardrail Prompt · Privacy + non-travel
Add two hard guardrails to the upload pipeline:
  1. Privacy: detect faces in uploaded photos and blur them client-side BEFORE the
     AI call. Discard the original file after analysis — never persist it.
  2. Non-travel: if GPT-4o returns confidence < 0.5 OR cannot identify a travel
     location/vibe, render a friendly error: "We can't fly there! Try a travel
     photo." Do not call the listings API in this branch.
Both guardrails must run on every upload, not just the first one.
Source Full chain in the repo: 03-prompt-chains/.
08 · The Handoff

Production-ready engineering spec.

The bridge between Lovable prototype and the team that ships V2 on real Airbnb data.

1
Architecture overview
Lovable React frontend → GPT-4o Vision API → mocked listings JSON. No backend persistence; photos discarded post-analysis. Single-page route, three screens, one model call per upload.
architecture.md
2
API + data contracts
GPT-4o response schema (location, vibe, confidence). Listings JSON shape (id, title, location_tags, vibe_tags, image_url, airbnb_url). V2 swap point is documented at /data/listings.json.
contracts.md
3
Known limitations & trade-offs
Listings are mocked (no live Airbnb integration). Visual similarity is hardcoded, not a real embeddings model. Latency is API-bound (~3–5s on cold start). Documented kill-switch thresholds.
limitations.md
4
Acceptance criteria
Upload → results < 5s p95 · face-blur applied 100% of uploads · non-travel error never calls listings API · first save event fires within 60s of landing on home for the test scenario.
acceptance.md

Before · the data signal
22% of visitors who clicked Create Wishlist from Photo abandoned at the upload screen without ever picking a file. AI analysis prompt surfaced it as the highest-impact finding: "users don't trust the AI will work; show them what it sees before asking for a save."

Added a transparent "We saw: a pink-pastel poolside villa in Bali" preview card on the results screen, BEFORE the listing carousel. One Persona-pattern prompt. Drop-off-equivalent journey time fell from 38s to 22s on the test scenario; save-rate trend pending more data.

10 · The Story

Friction · Learning · Aha.

The honest debrief — what broke, what I learned, the moment it clicked.

The Friction
My guardrails kept rewriting my features
Three times in M3, the face-blur prompt also nuked the listing carousel logic. I kept saying "add face blur" without grounding it in a constraint, and Lovable would happily rewire the whole upload flow. The fix was boring: write what must NOT change in every prompt.
The Learning
Constraint-grounding > clever prompts
My best prompts in M5 are the boring ones. "Keep all existing functionality working" added to every iteration prompt is what stopped the regressions. The cleverness lives in the architecture, not in the wording.
My aha moment was watching a classmate — not me, not a user I'd recruited — upload her own Santorini photo on day three of testing and silently save three listings. She didn't know I was watching. That's when I stopped seeing the product as a school project and started seeing it as the thing I'd been complaining about not existing for a decade.
