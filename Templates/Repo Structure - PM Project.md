# Repo Structure — PM Project

A canonical layout for a Vibe Coding PM project repo. Use this for any project you push to GitHub from Module 4 onward.

The goal is simple: a teammate clones your repo, opens it in any AI tool (Cursor, Claude, Lovable, ChatGPT with files attached), and the agent can answer any question about your product without you in the room. This is the workflow PMs are running at Indeed, Linear, Vercel, and other AI-fluent companies — your repo is the spec, the agent is the reading interface, and Confluence isn't in the picture.

---

## Why this matters

The Module 4 **Inheritance Test** is the proof. If your partner clones your repo and asks their agent "what does this product do?" — the agent will only answer correctly if your repo is structured for an agent to *read*. Disorganized repos produce hallucinated summaries. Well-structured repos produce briefings.

The structure below is what passes the test.

---

## The canonical layout

```
your-project/
├── README.md                    ← orientation for any human or agent (start here)
├── living-prd.md                ← the Living PRD (M4 Deliverable #3)
├── handoff.md                   ← Engineering Handoff Note (M4 Deliverable)
├── context.md                   ← background, company, user research, decisions log
├── prompts/                     ← Living Prompt Pack (from M3)
│   ├── design-system.md
│   ├── data-model.md
│   ├── components.md
│   └── structure.md
├── canvases/                    ← optional: visual summaries for Cursor / Claude
│   ├── product-overview.md
│   ├── user-flow.md
│   └── technical-architecture.md
├── prototypes/                  ← links and exports
│   ├── lovable-url.md           ← live Lovable URL + export instructions
│   └── screenshots/             ← key flow screenshots, design refs
└── src/                         ← refactored code (auto-synced from Lovable → GitHub)
    ├── components/
    ├── pages/
    ├── services/
    └── ...
```

## What goes in each file

### `README.md` — the orientation layer

The first thing any human or agent reads. Keep it short — under one screen.

Must include:
- **One-sentence pitch** — what this product is, who it's for
- **Status** — confidence line phase (M1 / M2 / M3 / M4 / M5 / M6) and what's real vs. mocked at a glance
- **Live URLs** — Lovable preview, deployed prod URL (if any), Supabase project
- **Where to read next** — a 3-line map: "For PMs read `living-prd.md`. For engineers read `handoff.md`. For background read `context.md`."

A teammate's agent will read this file first. If it's vague, the agent's summary will be vague.

### `living-prd.md` — the product spec

Your Module 4 Living PRD output. Eight sections:
1. Product Overview
2. Problem & Hypothesis
3. User Flows & Screen Map
4. Success Metrics
5. Technical Reality (real vs. mocked — be honest)
6. Assumptions & Risks
7. Scope (in / out / phased)
8. Engineering Recommendation

Generated by the Living PRD Extractor. Updated through M5 and M6.

### `handoff.md` — the engineering handoff

Your Module 4 Engineering Handoff Note. See `Templates/Engineering Handoff Note.md` for the template. Captures:
- Core intent & validated assumption
- Implementation status table (Real / Mocked per feature)
- Known hacks & technical debt
- Integration requirements (if extending an existing product)
- Success criteria for production
- Suggested architecture

### `context.md` — the briefing layer

This is what's missing from most PM repos and what makes an agent's summary go from "appears to be a dashboard" to "this is a B2B retention tool for PMs at series-B SaaS companies." Include:
- **Company / product context** — what business this lives in, who the user is, why this matters now
- **Decisions log** — key product calls you made and why (e.g., "We chose invite-first onboarding over feature-tour onboarding because the M2 hypothesis test showed 3x higher retention from social activation")
- **What you tried that didn't work** — failed experiments, killed directions, the no-go list
- **Open questions** — what you're still unsure about

The agent uses this to disambiguate everything else. Skip it and the agent guesses.

### `prompts/` — the Living Prompt Pack

Your M3 prompt chain, broken into the four discipline files. These do two jobs:
1. They let you (or a teammate) rebuild any part of the prototype from scratch
2. They let an agent understand the *intent* behind every component, not just what's on screen

### `canvases/` — optional, but powerful for Cursor users

If your team uses Cursor, this is where canvas markdown files live. Each canvas is a visual brief on one aspect of the product (overview, user flow, technical architecture). When a teammate opens the repo in Cursor, the canvases appear in the sidebar as readable visual summaries.

You don't need canvases for the Inheritance Test to work. They make the experience richer if your team is on Cursor.

### `prototypes/` — pointers and screenshots

The repo doesn't host the running prototype (that's in Lovable). It hosts the *pointers* to the prototype: live URLs, screenshots of key flows, export instructions. This way a teammate can find the prototype without asking you.

### `src/` — the code

Auto-managed by the Lovable ↔ GitHub 2-way sync. After your M4 refactor, the file names match your PRD (`OnboardingWelcome.tsx`, not `Component_1.tsx`). Includes the `README.md` Lovable generates during refactor.

## Naming conventions

- **Use kebab-case for markdown filenames** — `living-prd.md`, not `LivingPRD.md`. Agents and humans both parse it faster.
- **Prefix project-specific docs with the project name if needed** — `cadence-living-prd.md`, `cadence-handoff.md`. Only do this if the repo holds multiple products. For single-product repos, the simpler names above are better.
- **Don't use spaces in filenames.** Many AI tools URL-encode them and the agent shows broken links.

## What this looks like in practice

A teammate clones your repo. They open it in Cursor. They type:

> "What is this product, and what's the most recent thing the team decided?"

If your repo is structured per the above, the agent will:
1. Read `README.md` for the pitch and status
2. Cross-reference `living-prd.md` for the hypothesis and user flow
3. Pull recent decisions from `context.md`
4. Answer in a paragraph that sounds like *you* briefing them

If your repo is messy — code in `src/`, no markdown docs, no context — the agent will read 47 component files and give them a vague guess. That's the difference.

## How to validate your structure

Run the Module 4 **Inheritance Test** on your own repo:

1. Open your repo in an AI tool you haven't been using for this project (a clean context)
2. Ask the agent the 5 Inheritance Test questions:
   - What does this product do, and who is it for?
   - What hypothesis is it testing?
   - What's real vs. what's mocked?
   - What are the 3 biggest technical decisions an engineer needs to make next?
   - If you had to ship a fix on Friday, which file would you open first?
3. Compare the agent's answers to what you actually mean
4. Fix any gap

If you pass your own Inheritance Test, your repo is ready to hand to anyone.
