## Core Principle Established

### Every Module Must Have a Wow Moment

Carlos made this explicit and Dejan confirmed it as a design principle:

> "Every module should come with a wow moment, not only the first one. Every session you should have a wow moment in place."

This is now a **core principle for this program and any program Product School does.**

---

## Key Feedback on Module 2

### 1. Problem Framework Feels Slow and Theoretical

- Carlos: "The problem framework is slow. It felt like another theory block with a bunch of things that I already know."
- The concept didn't land as new or actionable. Students who've done any PM work will feel the same.
- **Fix needed:** Make it lighter and faster. Less theory, more action. Bring in reps — either the instructor doing it live or students doing it immediately.

### 2. Clarify: We're in the Solution Space

- Carlos: "Ultimately what we're building here is operating mostly on the solution space. That doesn't replace identifying the right problem — it just lets you provide solutions faster."
- Identifying the right opportunities is a different course (AI Product Sense / Strategy). This course accelerates solution validation.
- **Action:** Add one explicit clarification slide or callout: "This course operates in the solution space. Problem identification is outside scope — but we give you the constraints to make sure what you build actually tests the right thing."

### 3. Move "Never Start From Scratch" Content Earlier

- Carlos referenced a Reforge email: "Never start a prototype from scratch again."
- The Screenshot-to-App and Design-to-Code content (currently slides 12-13) should move UP — into the first teaching phase, right after 0-to-1 vs 1-to-N.
- **Why:** It connects directly to 1-to-N (import your design system, screenshot your existing product) and it's visually exciting — the kind of thing that wakes people up.
- Carlos: "This will wake people up. I think it connects really well with 0 to 1 versus 1 to n."

### 4. Figma + Code Partnership

- Carlos noted that Figma this week announced a partnership with code tools: **you can now start a design in code and bring it to Figma** (code-to-design, not just design-to-code).
- Not a full demo for this course, but worth highlighting as a trend: the design-code boundary is dissolving in both directions.

### 5. Credit Strategy Should Be in Module 1

- Carlos: "My suggestion would be to even put that in Module 1, so they don't learn too late."
- Students will burn credits in M1 if this isn't surfaced early. Dana already flagged this in the M1 session.
- **Action:** Move credit efficiency tips to M1. Can still reinforce in M2.

### 6. Prime 3 Things at Beginning, Breadcrumbs Throughout, Reinforce at End

- Carlos: "If it's three things — boom, boom, boom — clarifying at the beginning and making sure those three points are easy to follow in the module would help."
- Use consistent labels/titles throughout so students always know "I'm in way one, way two, way three."
- End with a summary that reinforces the same three points.
- Carlos: "I do that in all my presentations."
- **Action:** Define the three core things for M2 and thread them through the deck.

### 7. Module 2 Doesn't Feel Exciting — "I'm Leaving Not Excited"

- Carlos: "I'm leaving my Module 2 not excited. And that is what I wanted to express."
- The first class was "fireworks." Module 2 feels heavier on theory, lighter on action.
- Choosing a scenario is important but "it doesn't feel magical for students."
- **Risk:** Students start questioning whether they'll learn anything new or if they maxed out in M1.

### 8. The Wow Moment for M2: Context Injection

Carlos and Dejan converged on the idea of **bringing context into the prototype** as the M2 wow moment:

- How do you import existing product context? (design systems, screenshots, data)
- How do you incorporate feedback from users/customers/executives?
- Could be: connecting to a database, a Google Sheet, importing a file, using RAG, ingesting structured information
- Carlos: "If I can leave Module 2 with something that is just meaningfully better than what I built in Module 1, I think it's a perception, right? It's not just I learned something, it's also like I can see it."
- The prototype should look and feel **visibly better** than M1 — higher fidelity, more contextually relevant, more like a real product.
- Carlos: "How can you magically bring context in this session?"

### 9. Dana's Counterpoint on Backend

- Dana cautioned against going too far with backend connections (Supabase, etc.) too early — save complexity for later modules.
- The scenario commitment itself should provide meaningful progress.
- Carlos accepted this but insisted on **visual magic** — the prototype must look meaningfully better even without backend.
- **Resolution:** The wow comes from context (design systems, screenshots, imported data) rather than infrastructure (databases, APIs). Backend is for M5.
